# DarkDungeon

English | [日本語](README.ja.md)

A Windows / C++ / Qt prototype based on NetHack.

Source: https://github.com/fukuyori/DarkDungeon

## Running

Run `dist/DarkDungeon/DarkDungeon.exe`, choose English or 日本語 (Japanese), and start. The chosen language is used for menus, messages, item and monster names, quests and help. Adventures use NetHack's controls. Both languages include a guide under `Help > Play guide`.

The in-game `Language / 言語` choice takes effect on the next launch: save and exit, then restart from the launcher. English and Japanese use separate game engines and separate saves; an existing save cannot switch language.

The toolbar shows each action name below a 24-pixel icon and switches between one and two rows depending on the window width. Its buttons cover the basic action, inventory, wielding, tools, container contents, opening and closing doors, and going up or down stairs. The status panel follows the window width. Dungeon tiles start at 48 pixels and can be changed with Zoom in / Zoom out. Legacy 16-pixel tiles and 32-pixel equipment panels are moved to 48 / 24 pixels on first launch; other sizes are kept. Display settings are shared by both languages.

From top to bottom the window shows equipment and status, the dungeon, messages and the toolbar. The message pane is opaque and spans the full width.

In an adventure, Space chooses a basic action in this order: look inside a container at your feet, pick up, use the stairs, open an adjacent closed door. With no target it waits one turn. Multiple targets open a selection or a direction prompt.

## Display

Walls are drawn as thick dark-gray masonry and floors as light-gray flagstones, keeping the brightness difference between rooms and corridors. Characters and items are drawn over the terrain with transparent backgrounds, so the floor or stairs beneath them stay visible.

The hero and some monsters are drawn with the sprites in `sprites/`. The hero combines layers for role, race and gender, and the cape color shows alignment (lawful blue, neutral green, chaotic red). Moving one square plays a short walk animation; attacking plays a wind-up and strike. Combinations or monsters without sprites, and polymorphed, hallucinating or engulfed states, use NetHack's tiles. The sprites are generated by the Node.js scripts in `tools/sprites/`.

English saves, settings and scores are stored in `%LOCALAPPDATA%\DarkDungeon`, Japanese ones in its `ja` subfolder, separate from the original NetHack's locations.

## Building

Run from PowerShell 7. Requires the Visual Studio C++ tools, Qt 6.11.2 `msvc2022_64` and Qt's source license files. Use `-QtRoot` for the Qt location and `-NetHackSource` for the NetHack source.

```powershell
.\scripts\build-release.ps1
.\scripts\verify-runtime.ps1 -Language en -Native
.\scripts\verify-runtime.ps1 -Language ja -Native
```

The build prepares the English source in `build/nethack` and the Japanese source in `build/nethack-ja`. By default it builds both languages and the launcher; `-Language en` / `ja` builds only that game engine. The Japanese version uses a patch that ports the JNetHack translation to the specified NetHack 5.0.1. Its origin, license and save compatibility are described in [localization notes](docs/localization.md) (Japanese).

Lua data syntax and every role's quest table are checked during the build. Runtime checks use separate copies under `artifacts` and never touch normal saves or settings. They verify movement, language-specific item names and help, monster/object IDs in level data, sprite loading and animation, and save/restore, and they save screenshots. The Japanese checks also cover input echo and UTF-8 truncation boundaries.
`-Clean` rebuilds compiler output, which is also rebuilt when the toolchain or Makefile changes. The output's `provenance.json` records the source commit and the SHA-256 of the Japanese patch.
To test in a separate location while the game is running, use `build-release.ps1 -OutputRoot artifacts/ui-preview` and `verify-runtime.ps1 -ApplicationRoot artifacts/ui-preview`. Output locations are limited to subfolders of the project's `dist`, `artifacts` and `build`.
`DARKDUNGEON_SMOKE_OUTPUT` is for automated tests only: such launches use a fixed seed and a test save location and exit after the checks. Do not set it for normal play. NetHack's `NETHACKOPTIONS` / `NETHACKRC` are not inherited.

## Building on Linux and macOS

Linux (tested target: Ubuntu) and macOS (Apple Silicon) builds use NetHack's own Unix makefiles with Qt 6. Requirements: bash, git, GNU make, a C/C++ compiler, perl, pkg-config and Qt 6 (Core, Gui, Widgets). On Ubuntu, `qt6-base-dev` and `qt6-base-dev-tools` provide them; on macOS, Homebrew's `qt` and `pkg-config` (set `QTDIR` if Qt is elsewhere). The NetHack source must be a git checkout of commit `cb453720b1cdff0134f0872d8706fb20a764b0de` next to this project (or pass `--nethack-source`).

```bash
bash scripts/build-unix.sh                 # both languages and the launcher
bash scripts/build-unix.sh --language en   # English game engine only
./dist-unix/DarkDungeon/DarkDungeon
```

The output goes to `dist-unix/DarkDungeon`: the launcher, and `en` / `ja` folders that each hold a game engine with its data, saves and settings. The launcher points `NETHACKOPTIONS` at the engine's `darkdungeonrc`, so `~/.nethackrc` is not used. Rebuilding updates these folders in place and keeps saves.

Source changes shared with Windows are applied from `patches/darkdungeon-unix-en.patch` and `patches/darkdungeon-unix-ja.patch`. After changing `scripts/prepare-source.ps1`, run the Windows build and then `scripts/export-unix-patches.ps1` to regenerate them. The automated runtime checks (`verify-runtime.ps1`) and the installer are Windows-only for now.

## Installer

```powershell
.\scripts\build-installer.ps1 -PrepareOnly
.\scripts\build-installer.ps1 -Sign
```

`-PrepareOnly` only prepares the definition and staging folder. `-Sign` signs the launcher, both game executables, the installer and the uninstaller with the certificate named by `CODESIGN_CERT`, which may be a subject name, a SHA-1 thumbprint or a PFX/P12 file path. Use `CODESIGN_PASSWORD` for a PFX password if needed. Build output is not modified; a copy in the signing stage is signed.
