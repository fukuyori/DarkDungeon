## 1. 決定と未決定の境界

本書では共通の通信内容と観測を定める。2026-10-27、レモンが画面なし・画面ありの両方を選択した。[実行構成](agent-play-cli-runtime.md)で起動・接続・制御、[入力接続](agent-play-cli-inputs.md)でコマンド・入力・表示の全経路を定める。

以下のメソッド名と関連文書のCLI引数は実装する仕様であり、現行のゲームで利用可能という意味ではない。C0のレビューとコードの実装・動作確認を区別する。

| 項目 | 現在の扱い |

## 2. 責務と実行の境界

| 部分 | 責務 | コア状態へのアクセス |
|---|---|---|
| CLI／通信層 | UTF-8・JSONの検証、要求の識別、再送、受付状況、サイズ制限 | 直接読まない・変更しない |
| セッション管理 | 接続の識別、専用プロファイル、開始終了、要求記録と公開済み観測の保持 | 起動前の設定とコアからの通知を扱う |
| コアへの接続 | 入力待ちの分類、通常コマンドの配送、質問への応答、表示結果の受信 | コアの実行コンテキスト内でのみ扱う |
| 共通の表示用スナップショット | 表示を許された地図・状態・文章・選択肢を保持 | コアから受信したデータを所有する |
| Qt表示 | 同じスナップショットを使う描画、アニメーション、通常の手動入力 | 描画から名前生成・乱数消費・観察処理へ戻らない |

通信の読み取り処理が、処理中の`u`・`gi.invent`・`levl`・`glyphmap`などを直接参照してはならない。`busy`、再送、処理状況は通信側の受付記録から返す。処理中の観測は最後に公開した版を返し、`processing:true`とする。途中の状態を最新の観測として公開しない。

入力待ちへの到達と公開済み観測の交換を、同じ同期境界で行う。メニュー・文字入力・More等の入れ子の入力待ちでは、要求スタックを内部に保持する。外へ提示するのは一番内側の現在の要求だけとし、戻った親の入力要求には新しいIDを発行する。

画面なしはQtの`offscreen`起動ではなく、専用のGUI非依存の実行先で提供する。ウィジェット・モーダル画面・ディスプレイサーバーへの依存がないことをC1以降で実行検証する。

## 3. 共通の要求・応答

1レコードを1行のJSONオブジェクトとし、改行はLF、文字コードはBOMなしUTF-8とする。JSON文字列内の改行はエスケープする。入力はLF・CRLFを受け付け、重複キー、不正なUTF-8、NUL、JSONでない特殊数値を拒否する。

上限案は要求レコード1 MiB、応答レコード4 MiB。テキスト・メニュー等は後述のページ取得で分割し、黙って切り捨てない。上限を超えた入力レコードは行末まで破棄し、コアへ一切渡さない。接続が失われた場合の通知の可否は、通信路の設計に従う。

| 要求の項目 | 型 | 意味 |
|---|---|---|
| `api_version` | 整数 | 版1では`1`。未対応版は実行前に拒否 |
| `session_id` | 文字列／null | サーバー発行の起動単位の識別子。初期交渉だけnull |
| `request_id` | 文字列／null | 初期交渉だけnull。それ以外はセッション内で単調増加する10進整数。`1`から符号なし64ビット最大値まで。先頭ゼロは禁止 |
| `method` | 文字列 | 下表の操作名 |
| `expected_revision` | 文字列／null | コアへ作用する要求では必須。観測の版を10進整数文字列で指定 |
| `params` | オブジェクト | 操作ごとの入力。版1で未定義の項目は`invalid_params`として拒否 |

カウンターを文字列にするのは、クライアントのJSON数値の精度に依存しないため。座標・回数等の小さい整数はコアの範囲内のJSON整数とする。数量・汎用の数値回答は64ビットの値を扱う可能性があるため、10進整数文字列で表し、型変換で丸めない。具体的な形と範囲は入力接続に従う。

応答には`record_type:"response"`、`api_version`、`session_id`、`request_id`、`status`、`revision`、`processing`、`result`、`error`を持たせる。`error`は`code`とローカライズされた`message`を持ち、成功時はnull。状態は`completed`、`accepted`、`rejected`とする。読み取りの完了は`completed`。コアへ配送する要求は受付後の`queued`／`running`で`accepted`、次の入力待ちまたは終了に到達したら`completed`とする。`accepted`は適用済み・行動成功・ターン消費を意味しない。`request.status`自体の応答状態と、`result.request_state`で示す対象要求の状態は区別する。

1つの入力レコードに対する`response`は1つとする。新しい作用する要求は、入力待ちと版を検証して予約を確保した段階で`accepted`を返し、その応答を出力してからコアへ適用する。完了時に同じ要求への別の応答を自動送信しない。完了は`request.status`または同じ要求の再送で取得する。拒否は`rejected`、読み取り・初期交渉は`completed`を返す。

版1で自発的に出力するイベントは`session.ended`だけとする。`event`レコードの必須項目は`record_type:"event"`、`api_version`、`session_id`、`build_id`、`event`、`revision`、`created_utc`、`result`。`request_id`は持たず、必要なら`result.final_request`に最後の要求番号と完了要約を持つ。出力は単一の書き手で直列化し、少なくとも最後の作用する要求の受付応答より後に終了イベントを出す。クライアントは応答待ちでも`record_type`を見てイベントを別に処理する。終了イベント自体を質問や要求の完了応答へ読み替えない。

| メソッド | 分類 | 目的 |
|---|---|---|
| `session.hello` | 接続管理 | API版、実行先と共通コアのビルド識別子、起動時の言語・プロファイル、能力一覧、セッション、次の要求番号を報告。ゲームやプロファイルは新規作成しない |
| `session.start` | 起動・入力 | 起動時の言語・プロファイルとの一致を確認し、新規／再開を開始。選択の不足は質問として返す |
| `observe` | 読み取り | 現在の公開済み観測と現在の入力要求を取得 |
| `commands.list` | 読み取り | 対応済み操作ID、説明、構文、能力を取得 |
| `action` | コア入力 | 通常コマンドまたは方向付き移動を1回配送 |
| `prompt.respond` | コア入力 | 現在の入力要求へ1回応答 |
| `request.status` | 読み取り | 受付済みの要求が`queued`／`running`／`completed`／`rejected`／`expired`か確認。未受理を判定する手段にはしない |
| `messages.read` | 読み取り | メッセージの続きを取得 |
| `content.read` | 読み取り | 現在のメニューやテキストのページを取得 |
| `controller.set` | 制御 | 画面ありの操作者を切替。処理中なら入力待ちまで意図を保留 |
| `operation.interrupt` | 制御 | 指定した処理中の行動を、安全なコアの境界で中断する意図を記録 |

保存は`action`の`save`、終了は`quit`を通常のコアへ配送する。必要な確認には`prompt.respond`で応答し、自動的に肯定しない。新規／再開は1プロセスのセッションで一度だけ開始する。保存終了後や死亡後の再開は新しいセッションとする。

すべての要求は同じセッションの1本のCLI操作経路で順序を保って送る。認証済みのCLI接続は同時に1本とし、QtとCLIの操作者切替は実行構成に従う。

`session.hello`は`request_id:null`で、番号の消費・受付履歴への記録をしない。初回の`session_id:null`は接続先の既存の起動単位を照会する意味とし、起動・セッション新規作成の副作用を持たせない。以後はそのセッションIDを指定する。再送しても新しいゲームは作られない。起動引数と認証は実行構成に従う。

コアへ作用する`session.start`・`action`・`prompt.respond`は`expected_revision`を必須とする。起動前の公開済み観測も版を持ち、開始前の選択を無視してゲームへ進めない。

制御要求も要求番号・再送・受付記録の規則を使うが、ゲーム行動の予約とは別枠とする。`controller.set`と`operation.interrupt`は処理中にも受け付けられる。各種別につき保留1件までとし、別番号の追加の意図は`busy`で拒否する。制御意図を通信スレッドでコアの実体へ適用しない。

制御要求は構文・公開済み版・対象・操作者等を通信側の確定済みデータで確認し、専用の意図枠を確保して`accepted`を出力してから境界へ渡す。下記のゲーム入力用の予約と手順5〜6をそのまま適用して、処理中に中断や切替を送れなくすることはしない。

制御要求は受付時の公開済みの版を`expected_revision`で検査する。操作者切替は受付時の操作者の世代へ結び付け、次の安全な入力待ちで適用する。通常の行動完了で版が進むこと自体は意図を失効させない。別の操作者切替が先に適用された場合は`controller_overridden`で失効させる。GUIからの手動切替の意図はCLIの切替意図に優先する。

中断は`target_request_id`で現在進行中の`action`または`prompt.respond`へ結び付ける。最初の質問で元のactionが完了している場合は、その後に処理を進めた応答の要求番号が対象となる。対象が自然に終了した場合は`already_finished`として制御要求を完了し、次の行動を中断しない。対象が存在しない・該当するコア入力でない場合は`invalid_params`とする。通常の行動・質問の応答は、現在の操作者がCLIでない場合に`not_controller`で拒否する。

### 再送と受付の順序

1. レコードの構文、版、接続・セッション、項目の型を検証する。
2. 要求番号を照合する。同じ番号で内容が同じなら既存の受付結果・処理状況を返す。内容が異なり比較記録が残っていれば`request_conflict`とする。
3. 次の新規番号より小さく結果が保持されていない番号は、`request_expired`として拒否し、再実行しない。番号の飛び越しは`request_out_of_order`として拒否し、次に受付可能な番号を返す。この拒否では受付記録を作らず、番号も消費しない。
4. 新しい番号の要求では、まず受付記録を確保する。確保できなければコアへ渡さず`resource_limit`とする。
5. 作用する要求では観測の版、入力待ち、入力の内容を検証する。古ければ`stale_revision`、処理中なら`busy`、質問が違えば`stale_prompt`とし、コアへ渡さない。
6. 作用する要求だけをコアの実行コンテキストへ配送する。受付、適用開始、次の入力待ち／終了での結果を記録する。

受付記録と「作用する要求が予約済み」の状態は同じ排他区間で確保し、まだ実行を始めていなくても別の行動を予約させない。手順5の版・状態・入力内容の最終検証は、コアの実行コンテキスト内で適用と連続して行う。通信層で事前検証が成功していても、それだけで古い版の操作を実行しない。

同一内容は、JSONのキー順・空白を除く、型を区別した全項目の一致で判定する。番号を消費するのは手順4で記録を確保した要求だけで、手順5で拒否した場合も同じ番号では同じ拒否結果を返す。手順1での拒否、番号の飛び越し、記録を確保できなかった`resource_limit`では番号を消費せず、修正・復旧後の送信を新規として扱う。再送による重複判定は観測の版の検査より先に行う。

完了した作用・制御要求の直近1,024件と、読み取り要求の直近256件を別枠で保持する。未完了のゲーム行動1件と制御意図各1件も別に保持し、読み取りの件数で作用・制御要求を追い出さない。各記録は内容比較用のSHA-256、状態、8 KiB以下の結果要約とし、最大4 MiBの観測全体を各要求へ複製しない。読み取りの同じ内容の再送は、記録がある間は一致を確認して現在の公開済みデータで再評価する。作用・制御要求と拒否の再送は保持した結果要約を返す。古い番号は高水位で識別でき、記録を破棄しても再実行しない。

応答が届かない要求は、まず同じ番号・同じ内容で再送する。届いていなければ新たに受け付けられ、受け付け済みなら既存の状況・結果を返す。`request.status`は受付済みの番号だけを対象とする。番号不整合時は`session.hello`で次の番号を照合し、未適用と決めつけて別番号で行動を送り直さない。

`request.status`で照会要求自身や未受理の番号を指定した場合は`invalid_params`とする。要求の結果要約だけを返す応答の`revision`は、応答作成時点の最新の公開版とする。過去の適用版は`applied_revision`として区別する。観測本体を返す応答の`revision`は、その観測本体の版と一致させる。

クライアントは、結果を回収する前に大量の要求を送らない。セッションが変わった後は要求番号を引き継がず、プロセス停止前の要求が適用されたかを推測して再実行しない。新しい観測と保存済みのゲームの結果を確認する。

要求受付時の短い応答は`accepted`であり、後続の`request.status`で結果を確認する。コア側の最終検証で`stale_revision`等の拒否になる場合もあり、受付だけで行動成功とみなさない。行動が終わるまで通信をブロックして応答できなくなる実装にはしない。クライアントのタイムアウトは要求の取消ではない。

公開観測の版は、公開内容、現在の入力要求、操作者が変わったときに進める。コア内部だけの変化やアニメーションフレームでは進めない。地図だけが同じでも、次の操作の区切りには新しい版を発行する。読み取り・再送では進めない。処理中かどうかは応答の`processing`で示し、公開済み観測の内容と版に含めない。同じ版のスナップショットの中身を`processing`の切替だけで変えない。

主な機械向けエラーは、`invalid_json`、`invalid_utf8`、`record_too_large`、`unsupported_version`、`session_mismatch`、`invalid_params`、`request_out_of_order`、`request_conflict`、`request_expired`、`resource_limit`、`stale_revision`、`busy`、`wrong_input_state`、`stale_prompt`、`unsupported_command`、`invalid_choice`、`invalid_text`、`save_failed`、`session_ended`とする。通信の受付エラーと、コアが通常のメッセージとして示す行動の失敗は分ける。後者を隠れた情報に基づく事前エラーへ置き換えない。

接続と制御には`connection_busy`、`authentication_failed`、`not_controller`、`unsupported_view`、`controller_overridden`を加える。接続認証前の拒否とゲームAPIの応答は区別する。

### 要求のパラメーターと例

以下はワイヤー上の共通形の案で、実行手順ではない。

| メソッド | `params`の項目 |
|---|---|
| `session.hello` | 空オブジェクト。起動時の言語・プロファイルを応答で確認 |
| `session.start` | `mode`=`new`／`resume`。再開では、通常のセーブ一覧が提示した`save_id`を指定、または選択待ちへ進む。プロファイルや言語の変更は不可 |
| `observe`・`commands.list` | 空オブジェクト |
| `action` | `command`を必須とし、任意の`count`・`prefixes`とtoggle用`option`は[接続仕様](agent-play-cli-inputs.md)の構文だけを許可する。未対応引数を無視しない |
| `prompt.respond` | `prompt_id`と`response`。`response.type`で方向・品物・メニュー・確認・数量・文字列・位置・続行・取消・一覧表示を区別する |
| `request.status` | `target_request_id`。照会要求自身より前の受付済みの要求番号 |
| `messages.read` | `after`（そのセッションの通番、初回null）、`limit`（1〜100、省略時100） |
| `content.read` | `content_id`、0から始まる`page`。参照の有効期限を超えた場合は拒否し、現在の観測から取得し直す |
| `controller.set` | `owner`: `cli`／`manual` |
| `operation.interrupt` | `target_request_id`: 中断の対象となる現在のCLI行動の受付番号 |

移動要求の例。実際のセッションと観測の版を取得してから指定する。

```json
{"api_version":1,"session_id":"0123456789abcdef0123456789abcdef","request_id":"3","method":"action","expected_revision":"8","params":{"command":"movenorth"}}
```

応答が届かなければ、番号・内容を変えずに同じ要求を再送する。受付済みなら、次のような結果要約を返す。ここで`completed`は次の入力待ちへ到達した意味で、移動成功を保証しない。

```json
{"record_type":"response","api_version":1,"session_id":"0123456789abcdef0123456789abcdef","request_id":"3","status":"completed","revision":"9","processing":false,"result":{"request_state":"completed","applied_revision":"9"},"error":null}
```

続く観測で現在の入力要求を取得する。下は方向の質問に応答する例であり、通常の移動要求と混同しない。

```json
{"api_version":1,"session_id":"0123456789abcdef0123456789abcdef","request_id":"5","method":"prompt.respond","expected_revision":"10","params":{"prompt_id":"example-prompt","response":{"type":"direction","value":"north"}}}
```

処理中に`observe`を送った場合は、その要求自体は`completed`、応答の`processing`はtrueとし、結果のスナップショットは最後に公開した版のまま返す。取り違えを防ぐため、応答の`revision`は返したスナップショットの版とし、作用する要求の過去の適用版は`applied_revision`で別に示す。

## 4. 観測データ

| 区画 | 持つ情報 | 禁止・不在の扱い |
|---|---|---|
| `session` | API、ビルド、言語、通常／探索／デバッグの別、試験用乱数固定の有無、対応能力 | 種の値、内部乱数列、パス、認証用の値を含めない |
| `input` | `starting`／`command`／`prompt`／`ended`、現在の入力要求 | 観測時に質問への答えを補完しない。処理中は応答の属性で別に示す |
| `player` | 通常表示された状態欄の項目、主人公の表示座標 | 未表示の空腹の内部数値や内部耐性等を補わない |
| `map` | 原点・幅・高さ、表示済みの前景・背景、表示用の知識区分 | 実地形、全品物、隠れた敵の一覧を返さない |
| `inventory` | コアの通常一覧のスナップショット、invlet、表示文章、公開済み装備状態、一覧の版 | 観測のために`doname`・`xname`や鑑定処理を再実行しない |
| `messages` | 現在の通番、続きを取得する位置、欠落の有無 | 履歴復元を新規メッセージとして数えない |
| `result` | 終了した場合の理由、通常の結果表示、保存結果 | 保存ファイルの存在だけで保存成功を断定しない |
| `controller` | 画面あり／なし、現在の操作者 | 保留の切替を適用済みとして表示しない |

初期値や未取得の欄はnullとし、真の状態から埋めない。持ち物の一覧は、最後に正規の一覧生成をした版と取得時点を示す。取得済みの一覧が古いときはその旨を示し、最新化には通常の一覧操作を行う。メッセージ等を含めてサイズ上限に達する場合は、その区画の取得用参照を返してページ取得を可能にする。

正規の持ち物の一覧生成は、通常の`inventory`コマンドからコアが一覧を生成する時点と、品物選択で通常の一覧を提示する時点を基準にする。`update_inventory`等の変化通知ではキャッシュを古いと印し、CLIの観測を理由に名前を作り直さない。Qtの持ち物・装備欄も同じ生成済みの表示データへ接続し、再描画やズームで`doname`・`obj_to_glyph`を呼び直さない。常時表示の自動更新の範囲は、QtとCLIで同じ生成境界に揃えて確定する。

ターンの数値・差分・進行の有無は、コアが通常の表示設定で公開している場合にだけ返す。非公開時はnullとする。CLI-02・CLI-05の内部検証では、試験側だけで正確なターンと乱数を比較する。

メッセージは直近1,024件かつ合計4 MiB以下を保持する。取得は1回100件かつ64 KiB以下で分割する。通番はそのセッションで表示する新規メッセージだけに付け、抑止されたメッセージで進めない。取得位置はセッション内だけ有効。古い位置は`gap:true`と残存範囲を返し、新しい位置から続きを取れるようにする。セーブから戻した履歴は別の履歴区画として返し、新規の出来事へ混ぜない。

地図の座標はコアの座標をそのまま使う。今回の`global.h`では`COLNO=80`、`ROWNO=21`で、通常の有効座標はxが1〜79、yが0〜20。座標0列目を探索可能な床として返さない。範囲はビルドから取得して通知し、クライアントに固定値を埋め込ませない。

地図の知識区分は、`unexplored`、`remembered`、`current`、`detected`、`unspecified`とする。単なるglyph番号から現在見えると推定しない。`print_glyph`の受信に、コアが公開してよい知識区分を付ける接続が必要である。表示だけで確定できないものは`unspecified`として現在情報を補わない。視界の内部配列を通信層から取得しない。接続点と更新時点の網羅はC0の入力・表示対応表と合わせてレビューする。

コアが示した前景と、表示を許した背景だけを使う。対象の背後の地形が未表示ならnull。積み重なりの印があっても、全品物の個数・中身・下の対象を取得しない。検知・不可視の印・幻覚・擬態を実体へ戻さない。

地図上の名前は副作用のない表示上の説明に限る。品物の画像・外見の識別を返す場合はR2の外見グループへ正規化し、生のglyph・tileidx・真の種類を返さない。分類が未整備の場合はより粗い`item`等の表示分類へ留め、推測で詳細を埋めない。R3の静的台帳を通常の観測へ流用して実体の情報を補うことも禁止する。

## 5. 入力要求と応答

共通項目は`prompt_id`、`kind`、`text`、`cancel_allowed`、`default`、`constraints`、現在提示した選択肢を取得する参照。`prompt_id`は表示対象の内部ID・ポインター・物体IDから作らず、入力待ちごとに発行する。選択IDもその質問内だけで有効とする。

| `kind` | 応答の意味 | コア接続の対象と条件 |
|---|---|---|
| `direction` | `north`等8方向、許可された`self`・`up`・`down`・取消 | `getdir`の呼び出し元。キー割当から独立した方向をコアの方向入力へ変換し、混乱等の処理はコアを通す |
| `item` | 通常の持ち物にあるinvlet／質問内ID、コアが許す素手・なし、許可された数量、一覧を開く、取消 | `getobj`と床・容器選択。候補に強調されない`GETOBJ_DOWNPLAY`等も通常の選択経路で指定できるようにする。素手・なしは`HANDS_SYM`へ対応させ、適否はコア判定を通す。数量と対象を、単なる後続キーの残留にしない |
| `menu` | 選択IDと数量の配列、空選択、取消 | `select_menu`のPICK_ONE／PICK_ANY／PICK_NONEを区別。内部`anything`値は接続内部だけに保持 |
| `confirm` | 提示した選択のID、明示した既定値の採用、取消 | 汎用`yn_function`の呼び出し元。ESC以降の非表示選択肢を公開しない。既定値を自動実行しない |
| `number` | 許された範囲の整数、取消 | `get_count`や`yn_number`を使う呼び出し元。数量に続く対象／命令も同じ文脈で処理し、入力を別コマンドへ流さない |
| `text` | UTF-8文字列または取消 | `getlin`、名前・注記等。コアのバッファから得た上限を質問ごとに提示し、短い制限があればそちらを使う。今回の一般行上限は英語255バイト、日本語511バイト、名前は双方31バイト。固定値をクライアントへ埋め込ませない |
| `position` | 位置、決定方法、取消 | `getpos`と`readchar_poskey`。隣接方向の`CMDQ_DIR`で任意座標を代用しない。クリック入力に相当する座標の経路と、必要な決定方法を設計する |
| `continue` | 続行、ページ送り、許可された取消 | メッセージのMore、ブロックするテキスト・物語・ヘルプ。説明の取得だけで続行したことにしない |
| `selection` | 提示された開始・再開・職業・種族・性別・属性等の選択 | Qt固有の開始前の流れも含む。候補と許可マスクを共用し、独自のキャラクター条件を作らない |
| `command_selection` | 公開した完全名の操作ID、取消 | `get_ext_cmd`の追加の選択待ち。通常コマンド待ちと区別し、特権・内部専用を候補へ出さない |
| `key` | 呼び出し元が明示した単キーの意味 | 物のクラスや調べるキー等、通常の単キー質問だけを分類する。自由なキー列へ逃がさない |
| `unsupported` | 応答は拒否し、理由を返す | 分類できない`nhgetch`等。入力待ちを検出可能にするが、必須経路に残っていればC1／C2の完了にしない |

方向・品物・位置の識別は翻訳文を解析せず、該当するコア関数を入口にして種類を付ける。一般の`yn_function`だけでは方向と品物を区別できない。汎用関数の既存シグネチャを一括で推測変更せず、追加するC互換の接続を原本とUnix用パッチで揃える。

取消、空選択、既定値、一覧表示の要求は別の意味として表現する。数量は整数とし、全数の指定はコアの許可する明示的な値へ変換する。符号や`-1`等の内部表現を、意味を説明せず外部へ要求しない。

CLI版1は、内部文字列もUTF-8で扱うビルドを対象とする。Windowsの既存の`build-release.ps1`は`IC_UTF8=Y`を渡し、日本語Makefileではこれが`/source-charset:utf-8 /execution-charset:utf-8 -DICUTF8`になる。Unixの日本語ビルドも`ICUTF8`を指定している。日本語C++フラグから`/utf-8`を外す行だけでSJISと判定してはならない。現在の生成済み`global.h`は英語BUFSZ=256、日本語BUFSZ=512であることも確認した。

英語版については、既存の`fromLatin1`等を維持したまま対応済みとは扱わない。追加要求の英日対応と、既存のCLI-06のUTF-8入力に従い、英語版のC/C++ビルド指定、入力・名前の保持とバイト境界、Qtの文字列変換もUTF-8へ揃える変更をC1の必須作業に含める。英語版をASCII入力だけに制限する方針へ縮小しない。`ICUTF8`は日本語用の定義なので、英語版への対応をそのマクロの有無だけで判定せず、両方のビルドに共通の文字コード情報と実際の入出力で確認する。これらは今後必要な変更であり、現行の英語版で実装・検証済みという記述ではない。

CLIの起動時には対象ビルドの内部文字コードとバッファ上限を確認する接続を設け、不一致のビルドでは開始前に失敗する。別の文字コードを黙ってUTF-8として扱わない。UTF-8以外のコアを扱う拡張を行う場合は、変換後の内部バイト数、変換不可文字、往復変換の保持を別途設計する。現在の実行ファイルや未実行OSでの文字コード確認は、ビルド指定のソース確認と区別する。

位置の決定方法は`traditional`、`quick`、`once`、`verbose`とし、`getpos`の通常の`.`・`,`・`;`・`:`の意味へ対応させる。ユーザーがキーを変えても意味を維持する。位置選択中の自動説明は、コアが通常表示したメッセージとして返す。直接座標の確定方法と、カーソル移動・説明の手順を混同しない。

メニューのページ取得は1回最大100項目、テキストはUTF-8で64 KiB以下を案とする。同じ入力要求の内容を固定してページを返し、ページ移動で選択・時間進行・乱数消費を起こさない。選択結果は全ページ共通の質問内IDで指定できるようにする。

## 6. 通常コマンドとの対応

`extcmdlist[].ef_txt`の英語の完全名をIDに使い、通常のコアの実行可否判定と拡張コマンド配送を通す。関数を通信層から直接呼ばない。キーが未割当でも実行できる経路を用意し、既存ツールバーと共通化する。

`commands.list`は静的な対応表と公開済み能力から作り、行動時の`can_do_extcmd`やLuaの実行前コールバックを先に呼んで判定しない。これらは実際のコマンド配送時だけコアが実行する。

| 操作例 | コアのID | 扱い |
|---|---|---|
| Space相当 | `contextaction` | 通常の基本動作。CLIで箱・品物・階段・扉の順序を再実装しない |
| 足元の容器 | `lookcontainer` | 通常の箱・袋の確認と選択へ進む |
| 移動 | `movewest`等8方向 | 標準の歩く操作。敵にぶつかる等の結果はコアが決める |
| 持ち物・装備 | `inventory`、`wield`、`wear`、`puton`、`remove`、`takeoff`、`swap`、`quiver` | 後続の質問を構造化し、未処理の品物キーを次のコマンドへ残さない |
| 探索・道具・消耗品 | `search`、`wait`、`apply`、`eat`、`quaff`、`read`、`loot`等 | 時間を進めるかはコアの結果による |
| 戦闘・魔法 | `kick`、`throw`、`fire`、`cast`、`zap`等 | 方向・品物・呪文・位置・確認をその都度要求 |
| 扉・階段 | `open`、`close`、`up`、`down` | 通常のコアへ配送 |
| 調査 | `look`、`glance`、`whatis`、`lookaround`等 | 操作の結果として許される説明だけを取得 |
| 保存・終了 | `save`、`quit` | 通常の確認を省略しない。終了結果は別に返す |

C0の対応表は上の例だけで完了しない。ビルドで有効なコマンドを列挙し、通常操作、接頭辞、操作環境の機能、内部専用、未ビルド、特権用へ全件分類する。内部専用の`containermove`・`clicklook`等、未ビルドの機能、通常モードの`WIZMODECMD`を通常エージェントの呼び出し口へ出さない。利用不能の理由を隠れた地形や品物の正体から生成しない。

## 7. 専用プロファイルと保存

プロファイルIDは英数字と`-`・`_`だけ、1〜64文字とする案。IDをパスとして解釈しない。明示したプロファイル用ルートの下に、言語ごとのコアデータ・設定・ログ・通信記録を置く。Qtを使用する場合はQSettingsも分ける。DATAPREFIX等の読み取り専用データ参照と、コアの書き込み用prefixを区別する。

通常の`%LOCALAPPDATA%\DarkDungeon`へ暗黙に戻らない。プロファイルを作れない場合はゲーム開始前に失敗する。既存のデータがあるプロファイルで新規開始するときは、既存セーブの扱いを明示し、黙って上書きしない。プロファイルの排他は、コアの保存ロックを置き換えず追加で管理する。

乱数固定はプロファイルと独立した試験ハーネスの起動設定とし、通常のプレイ用要求では種を変更できない。`DARKDUNGEON_SMOKE_OUTPUT`に伴う乱数固定・保存先変更・自動検査・自動終了には依存しない。

`dosave`は確認後に`dosave0`が成功すると`savefile_completed`を増やし、Moreを経て`exit_nhwindows`と終了へ進む。保存通知はこの成功経路から生成し、そのMoreの観測で`result.save:"succeeded"`を公開する。ファイルのタイムスタンプで推定しない。Moreは自動続行せず、エージェントの応答を待つ。保存失敗でゲームへ戻る経路も通知する。死亡・勝利等でも、通常の公開・確認が済むまで必要な質問を返す。

正常終了では`exit_nhwindows`より前の接続で、進行中の最後の要求を完了記録へ更新し、`session.ended`の最終イベントを生成する。新しいセッションには新しい`session_id`を発行し、専用プロファイルの通信記録領域`control/<session_id>/terminal.json`へ一時ファイルからの置換で保存する。イベントは第3節の共通形を使い、セッションID・ビルド識別子・作成時刻を含む。他のセッションのファイルを上書き・再利用しない。

通信路へも同じ終了イベントを出力・フラッシュする。受信側は初期交渉で取得したセッションID・ビルド識別子と一致する結果だけを採用し、結果とプロセス終了を別々に確認する。不在・不一致は結果不明とし、前回の結果を今回の成功へ流用しない。出力に失敗しても、そのセッションの最終結果から確認できるようにする。保存・記録に失敗した場合と突然の停止では、結果が不明な場合を成功や未実行として推測しない。ファイルの確認は実行構成の`result --session`で行う。

通常モードの`restore.c`では復元後に`delete_savefile()`を呼ぶことを確認した。検証用の元セーブは直接起動に渡さず、専用プロファイルへコピーする。探索・デバッグモードと通常モードの違いをセッション情報と結果に記録する。

プロセス停止・再開で`session_id`、観測の版、質問IDを再発行する。古いメニューID、選択ID、要求番号を新しいゲームへ引き継がない。通信記録をゲームのセーブへ混ぜず、再開したゲームの観測から判断し直す。

`session_id`はOS側の乱数を使う識別子とし、ゲーム本体・表示用の乱数を消費せず、起動をまたいで同じ値を使い回さない。通信記録用ディレクトリは新規作成で排他的に確保し、既存と衝突したら別の識別子を作る。既存の記録を上書きして開始しない。古い通信記録の削除は通常プレイで自動実行せず、保存方針を起動・管理の詳細設計へ含める。
