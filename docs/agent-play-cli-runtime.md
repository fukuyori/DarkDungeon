# C0 起動・接続・画面あり／なしの構成

状態: C0の設計を2026-10-27に確定。レモンが「画面なし・画面ありの両方」を選択した。以下のファイル名・引数・機能は実装する仕様であり、現行の実行ファイルで利用できることを示すものではない。

## 1. 実行先と共通コア

| 実行先 | 役割 | Qtの使用範囲 |
|---|---|---|
| `DarkDungeon-cli` | 起動、セッションの指定、端末の行コマンド、エージェント用JSON Linesの中継 | Qt Core・Network。コンソール用 |
| `DarkDungeon-agent-en`／`DarkDungeon-agent-ja` | 画面なしの通常ゲーム。専用のagentウィンドウポートを使用 | Qt Core・Networkだけをリンクし、QCoreApplicationを1つ使用 |
| `en/DarkDungeon-en`／`ja/DarkDungeon-ja` | 既存Qtゲームへ同じ操作APIを接続した画面ありの実行先 | 既存のQApplicationを1つだけ使用し、共通の操作接続を追加 |
| `DarkDungeon` | 既存の通常プレイ用ランチャー | 通常の言語選択と起動を維持 |

Windowsでは`.exe`を付ける。配置はCLIをアプリ直下、画面なし／ありの言語別実行先をそれぞれ`en/`・`ja/`の下とする。CLIは言語別の同梱先を選択し、PATHや現在の作業ディレクトリから別のゲームを探さない。

言語ごとに、通常ルール・データ・乱数処理を持つCコアを共通のライブラリに分離し、起動処理・ウィンドウポート登録・表示先を画面あり／なしの各実行先へ結合する。Qt Widgetsを参照する処理を画面なしのリンクへ含めない。`windows.c`の登録表やOSの起動処理等、表示先で異なる部分はライブラリの外へ分ける。共通の変更原本とコアのコンパイル定義を記録し、ゲームルールに関係する差を別々に持たせない。

画面なしにも表示情報の意味を処理するためのタイル／glyph対応表は必要だが、PNG、タイル画像、Qt GUI、画面、ディスプレイサーバーを要求しない。表示先の追加と`TILES_IN_GLYPHMAP`の共通設定は生成処理へ組み込み、glyph番号を独自に振り直さない。Qtの`offscreen`で画面を隠す方法は画面なしの完成条件に使わない。

既存のQt通常起動はCLIを有効にしない。操作APIを使う画面ありゲームは、CLIの`start --view gui`で専用プロファイルから起動する。この版では、APIを有効にせず起動済みの通常ゲームへ、後付けで操作機能を注入することはしない。

背景の情報保護と公開済み地形の補助記録は、通常のQt起動でも同じ規則を使う。通常起動では、通常の言語別データ保存先の`knowledge/`に補助記録を置く。CLI用の設定先やIPCは有効にせず、従来のゲーム本体のセーブ形式も変えない。専用起動と通常起動で、視界外の実地形から背景を補う規則を分けない。

### 共通コアのコンパイル分岐

C0で調査した移行前のソースのQt依存条件は、英日とも14箇所だった。移行前の参照台帳は[英語](data/agent-core-port-branches.en.json)・[日本語](data/agent-core-port-branches.ja.json)。ファイル・条件・出現番号・元ファイルのハッシュを持ち、参照にない分岐や未分類のファイルは静的な検査で失敗させる。C1の移行後の台帳と確認結果は[実装・検証記録](agent-play-cli-implementation.md)を参照。

| 現行の場所 | 条件の数 | C1での分離先 |
|---|---:|---|
| `include/config.h` | 1 | 共通のタイル意味・終了表示の能力とGUI専用のXPM等を分離 |
| `include/global.h` | 1 | `TILES_IN_GLYPHMAP`とglyph構造の設定を共通化 |
| `include/extern.h` | 1 | 音声の呼び出しを表示先の能力へ分け、Qtのリンクを要求しない |
| `src/cfgfiles.c` | 4 | `qt_tilewidth`・`qt_tileheight`・`qt_fontsize`・`qt_compact_mode`へのextern参照を共通の素のCデータへ移す |
| `src/options.c` | 1 | 状態表示の更新を実行時の表示能力へ接続 |
| `src/mdlib.c` | 1 | ポート名・既定値・ビルド情報を実行時の登録情報へ接続 |
| `src/windows.c` | 2 | 表示先の登録表をライブラリの外へ置く |
| `sys/windows/windsys.c` | 2 | 保存先と試験用の種の取得をGUI非依存のランタイムへ接続 |
| `sys/windows/windmain.c` | 1 | 入口を分け、agentでconsolettyを開始しない |

共通Cコアは両実行先で同一の定義・オブジェクトを使い、`QT_GRAPHICS`をライブラリの機能判定に使わない。追加する表示非依存のアプリ定義`DARKDUNGEON_APP`と共通能力を用い、`TILES_IN_GLYPHMAP`・`DEFAULT_WC_TILED_MAP`・終了表示の呼出し能力を揃える。Qtヘッダー、XPMの読込、Qt Widgetsの変数・関数はGUI側だけへ置く。

設定の受け皿は追加する素のCのview設定データとし、Qt側が起動時・変更通知で読む。ウィンドウポートの既定名と列挙も実行時の登録情報から取得し、Qtをリンクしない共通ライブラリへ`DEFAULT_WINDOW_SYS="Qt"`を固定しない。音声等は、共通設定と表示先の能力を区別する。

C1では分岐の移行と書換え後の台帳をレビューし、生成の前後で未分類があればビルドを失敗させる。共通ライブラリのコンパイル定義・オブジェクト一覧・ハッシュ、および`glyph_map`・`glyph_info`・`window_procs`等のABIを照合する。C0時点では台帳と移行方針の確認までで、分離後のリンクは未確認だった。C1で実施した範囲は実装・検証記録へ分けて記載する。

## 2. 起動と端末コマンド

以下は実装後の利用例。`start`は接続先の準備までで、ゲームの新規開始・復元は行わない。準備済みの起動単位に対し、JSON APIの`session.start`または行コマンドの`new`／`resume`で冒険を始める。

```powershell
.\DarkDungeon-cli.exe start --view headless --language ja --profile agent-01
.\DarkDungeon-cli.exe start --view gui --language ja --profile watch-01
.\DarkDungeon-cli.exe connect --session <session-id>
.\DarkDungeon-cli.exe new --session <session-id>
.\DarkDungeon-cli.exe observe --session <session-id>
.\DarkDungeon-cli.exe act --session <session-id> movenorth
.\DarkDungeon-cli.exe act --session <session-id> contextaction
.\DarkDungeon-cli.exe result --session <session-id>
```

| コマンド | 内容 |
|---|---|
| `start` | `--view headless|gui`、`--language en|ja`、`--profile <ID>`を必須にする。専用の実行先を起動し、接続準備の成功を待つ |
| `sessions` | その利用者の専用プロファイルのセッション一覧と接続可能性を表示する。PIDだけで稼働中と断定しない |
| `connect` | 1本の継続接続で、標準入力・出力を共通仕様のJSON Linesとして中継する |
| `new`／`resume` | 新規／再開を`session.start`へ配送する。必要な開始時の選択は応答として返す |
| `observe`／`commands` | 現在の観測／対応済みコマンド一覧を取得する |
| `act` | 完全名のコアコマンドと、対応表で定義した引数を配送する |
| `respond` | `--prompt`、`--revision`、`--response-file <JSONファイル>`で現在の質問へ応答する。対象の版を省略して自動で肯定しない |
| `save`／`quit` | `act save`／`act quit`の別名。コアの確認へ進むだけで、自動的に肯定しない |
| `status` | 受付済み要求の結果を確認する |
| `control` | 画面ありで操作者を`cli`／`manual`へ明示的に切り替える |
| `interrupt` | 後述の安全な境界で中断できる連続行動へ、中断の意図を送る |
| `result` | 指定セッションの最終結果ファイルを読み、ID・ビルド一致を確認して返す。ファイルがなければ結果不明とする |

機械向け出力を既定とし、診断は標準エラーだけに出す。人向けの整形は`--human`で選ぶが、`connect`では使用できない。例の`<session-id>`は`start`のJSON出力で得た値を使う。

単発のコマンドの出力は`record_type:"cli_result"`、`cli_version:1`、`command`、`session_id`、`request_id`、`result`、`error`を持つ1つのJSONとする。作用するコマンドでは、`request_id`に照会用ポーリングの番号ではなく実際のゲーム入力の受付番号を残す。元のAPI応答・最終イベントは`result`内に区別して返す。`connect`はこの外側の形式を付けず、共通APIのresponse／eventだけを中継する。

`act`の構文は`--count <整数>`、順序を保つ最大2つの`--prefix <名前>`、toggle用の`--option <正式名>`に対応する。`respond`のファイルはresponseオブジェクトそのものとし、任意のコマンド列を実行しない。`--data-root`は後続のコマンドでも同じ値を指定できる。

単発の行コマンドも同じIPCとAPIを使い、コアをもう1つ起動して操作結果を計算しない。接続を確保し、初期交渉で次の要求番号を取得する。`act`の版を省略した端末操作では公開済み観測を1回取得してその版を使う。途中で状態が変わった場合は失敗を表示し、自動再適用しない。エージェントが厳密に制御する場合は、`connect`から要求番号・版を明示する。

単発の作用コマンドは`accepted`を受け取った時点で接続を閉じ、その後は`status`の確認ごとに接続し直す。100 ms間隔で最大30秒確認し、確認の合間は別の単発の中断・操作者切替が接続できる。読み取りの確認が`connection_busy`なら期限内で後に確認するだけで、行動を再送しない。次の入力待ちに戻れば結果を返す。待ち時間超過では受付番号と処理中の結果を返し、取消や未実行と見なさない。`--timeout-ms`はクライアントの待ち時間だけを変える。

CLI自身の終了コードは、0=成功または必要な次の入力待ちを返した、2=引数・入力不正、3=起動・接続・認証失敗、4=API拒否、5=受付済みだが待ち時間超過、6=結果不明・異常終了とする。ゲーム内の攻撃失敗等は、APIが正常に実行できたなら通常の観測・メッセージとして返し、接続失敗へ読み替えない。

## 3. IPCと接続の所有

ローカル通信はQt Networkの`QLocalServer`／`QLocalSocket`を使う。TCPは待ち受けず、Linuxの抽象ソケットも使わない。サーバーはゲームの通信専用スレッドに置き、同スレッドのイベントループで認証、読み取り、`busy`、再送と結果の問い合わせを処理する。通信層はコアの構造体を読まない。

画面なしのコアは、agentウィンドウポートの入力待ちで条件変数等により型付きの要求を待つ。通信側は入力データを渡すだけで、コアの関数を呼ばない。画面ありでも、Qtへの通知は要求の到着を伝えるだけとし、イベント処理の中からゲームコマンドを再入実行しない。

1つのセッションに、認証済みのCLI接続は同時に1本だけを許可する。2本目は`connection_busy`として拒否する。単発コマンドが切断した後、次のコマンドは同じセッションへ接続できる。継続接続があるときは別の単発操作を混ぜない。要求番号・受付記録は接続ではなくゲームの起動単位に属し、再接続で初期化しない。

セッションごとの接続情報を専用の記録領域へ置く。内容はセッションID、ビルド、言語、view、プロファイル、実行先、PIDと起動識別情報、IPC接続先。接続先のパスだけを接続認証の根拠にしない。OSの乱数で作った256ビットの共有値を別の利用者専用ファイルへ置き、CLIは後述の相互チャレンジ応答にだけ使う。値そのものを通信、プロセス引数、通常の観測、診断、利用者向けJSON出力へ出さない。

セッションIDはOSの乱数128ビットを表す32桁の小文字hexとする。CLIはそれ以外の形式を拒否し、IDを任意のパスとして扱わない。セッションの検索は専用ルートの有効なプロファイルID・en/ja・control配下の接続情報だけに限定する。ゲームのセーブや任意のファイルを再帰検索しない。

認証はゲームAPIと別の接続手順であり、成功後に`session.hello`を許可する。認証前の上限は4 KiB、5秒とし、失敗時は接続を閉じる。利用者向けのAPI要求には認証値を含めない。記録ファイルと親ディレクトリのアクセスを利用者に限定し、WindowsではDACL、Unixではディレクトリ0700・秘密ファイル0600を使う。

接続名にもOSの乱数128ビット以上を含める。認証はHMAC-SHA256を使う。クライアントが32バイトの新しいnonce Cを送り、サーバーが32バイトのnonce Sとサーバーのタグを返す。クライアントはタグを検証してからクライアントのタグを返し、サーバーが検証して認証成功を返す。サーバーが共有値を持つことを確認する前にクライアントのタグを渡さない。

タグの入力は`dd-agent-auth-v1`、役割`server`または`client`、セッションID、ビルド識別子、Cの小文字hex64桁、Sの小文字hex64桁を、この順にNULで区切ったBOMなしUTF-8（末尾NULなし）。キーは共有値の32バイトで、タグも32バイトの小文字hexで送る。両nonceは接続ごとに再生成し、役割を分離してタグの使い回しを防ぐ。固定長タグの比較を途中で打ち切らず、共有値・タグ・nonceを通常ログへ出さない。

`QLocalServer::UserAccessOption`を`listen`前に設定する。ただしmacOSではソケットの許可フラグが効かないため、親ディレクトリの保護と上記の接続認証も必須にする。Unixのソケットは利用者専用の短い実行時ディレクトリへ置き、OSのパス上限を事前検査する。長いプロファイル名・保存先をソケットのパスへそのまま連結しない。[QtのQLocalServer仕様](https://doc.qt.io/qt-6/qlocalserver.html)

接続済みのゲームへ`start`で重ねて接続したつもりにしない。プロファイル排他で二重起動を拒否し、既存のセッションIDを案内する。残ったソケットの名前やPIDだけを根拠に、別プロセスの終了・ファイル削除・`removeServer`を自動実行しない。

## 4. 起動の順序と保存先

1. CLIが必須引数・実行先・言語データ・viewを確認する。
2. 専用プロファイルを確定する。既存のセッションがあれば案内するが、CLI側の事前照会だけで排他を保証したことにしない。通常のプロファイルへ戻る経路を作らない。
3. 新しいセッションID、通信記録領域、利用者限定の接続情報を作る。
4. 実行先へ非公開の起動設定ファイルの場所を渡す。実行先自身がその言語・プロファイルのプロセス寿命に結び付くOSの排他を取得し、コアのファイル・設定初期化より前に保存先を設定する。排他は実行先が保持し、起動したCLIが終了しても解放されない。二重起動では一方だけがコア初期化へ進む。
5. 画面なしはQCoreApplication、画面ありは既存のQt初期化によりQApplicationを1つだけ作る。既存の`NetHackQtBind`と別のQApplicationを追加して二重生成しない。
6. IPCと公開済みの`starting`観測を用意し、接続準備完了を通知する。`session.start`までキャラクター生成・セーブ消費・冒険の入力を始めない。

画面なしは専用mainの冒頭でQCoreApplicationを作る。画面ありは`qt_init_nhwindows`内の`new NetHackQtBind`より前にQt設定の形式・`config/qt/`への絶対パスを固定し、構築中のQSettingsを通常の設定へ向けない。既存のアプリインスタンスがあるのに新しいQApplicationを作る経路は失敗させる。通信用QObjectとスレッドは、それぞれのアプリインスタンスの構築後に作る。

コアの`askname`・`player_selection`・セーブ選択・復元より前に、新しく設ける共通の開始ゲートを通す。そこで`starting`を公開して`session.start`を待ち、その結果でのみ先へ進む。Qt独自の開始画面の`startGame`等も同じゲートへつなぎ、APIの開始待ちをすり抜けない。

`start`の準備待ちは30秒とし、超過しても起動先を無条件に強制終了しない。生成したセッションIDと確認状況を返し、接続準備の成功を確認できなかったことを示す。画面なしのWindows実行先はコンソール用で作り、CLIから起動するときは新しい可視コンソールを作らない。画面ありは選択したQt画面を表示する。

起動処理は実行先をCLIから独立して存続させ、CLIのプロセスオブジェクトの破棄で実行先を終了しない。準備完了はファイルができたことだけで判断せず、IPCの認証と`session.hello`で対象のID・ビルドを照合する。画面なしは、コア初期化前のエラー、設定、回復や終了でもMessageBox・スプラッシュ・GUI選択画面を作らず、診断と型付きの応答へ出す。

Windowsの画面なし起動は`CREATE_NO_WINDOW`と新しいプロセスグループを用い、CLIのコンソールと制御イベントを共有しない。Unixでは新しいOSセッションへ分離し、CLIの制御端末を持たせない。stdinはNUL／`/dev/null`、stdout・stderrはセッション別ログへ向ける。コア出力をCLIのJSONへ継承しない。`nt_kbhit`・`kbhit`・`pgetchar`もagent入力と中断フラグへ接続し、端末のキーやEOFを読ませない。実行先自体へのOSの終了シグナルは、通常の終了・回復経路の範囲として接続の切断と区別する。

Unixの新しいOSセッションへの分離とstdioの付け替えは、画面ありにも適用する。Windowsの画面ありはGUI用実行ファイルとして独立して起動し、CLIのコンソールのハンドルを継承しない。両viewとも、起動した端末やCLIが閉じられたことをゲームのhangupへ結び付けない。

既定の専用ルートはWindowsが`%LOCALAPPDATA%/DarkDungeon-agent`、Linuxが`${XDG_DATA_HOME:-$HOME/.local/share}/DarkDungeon-agent`、macOSが`~/Library/Application Support/DarkDungeon-agent`。通常データのディレクトリと兄弟に置く。`--data-root`で明示的な別ルートを指定できる。書き込み先は`<root>/<profile>/<language>/`に限定し、プロファイルIDをパスとして解釈しない。

| 相対配置 | 内容 |
|---|---|
| `game/` | セーブ、階層、ロック、スコア、骨、コアの書き込みデータ。prefixごとの配置は初期化で明示 |
| `config/nethackrc` | そのプロファイルだけのNetHack設定 |
| `config/qt/` | 画面ありのQSettings。通常の組織・アプリの設定先から分離 |
| `logs/` | 起動・診断ログ。認証値を含めない |
| `control/<session_id>/` | 接続情報、受付記録、最終結果。セーブとは別のライフサイクル |
| `knowledge/` | 保存と厳密に結び付けた、公開済み地形だけの表示用補助記録 |

言語別のゲームデータ・ライセンス・`DATAPREFIX`はアプリの言語ディレクトリを読み取り専用で参照する。書き込み用prefixをアプリ配置先へ戻さない。Unixの現行`VARDIR`、Windowsの現行の通常保存先、`NETHACKOPTIONS`・`NETHACKRC`の初期化、QtのQSettingsをすべて照合する。

コアの全prefixと設定先は絶対パスにする。Qt初期化で作業ディレクトリがアプリの配置先へ変わっても、そこへ書き込みを起こさない。

WindowsのパスはOSとの境界でUTF-16へ変換し、コアへ保持するパスのUTF-8と混同しない。既存の`CreateDirectoryA`等を残して非ASCIIの保存先を成功と報告しない。コア側のパス長制限を超える場合は開始前に失敗し、切り詰めや通常保存先への代替をしない。

既存セーブの再開では元のセーブを通常のコア経路で扱う。検証ではコピーを使い、セーブ消費・保存失敗・ロックを英日それぞれで試験する。インストーラー、署名、公開、通常の`dist`の上書きはC0・C1の完了に含めない。

## 5. CLIと手動操作の切替

専用起動の初期操作者は両viewとも`cli`。画面ありには、通常のゲーム情報と現在の選択肢を表示し、CLI操作中も入力待ち・画面更新が止まらないようにする。CLI所有の質問をQtの操作必須のモーダル画面だけに閉じ込めない。

画面ありは`controller.set`で`cli`／`manual`を明示的に切り替えられる。CLI所有中は通常のQtキー・マウス・ツールバーからのコア入力を抑止し、ウィンドウ操作と操作者切替は使えるようにする。手動所有中はCLIの読み取りを許可するが、通常の行動・質問への応答は`not_controller`で拒否する。

抑止は見た目の無効化だけでなく、keybuffer・clickbuffer・メニューのゲーム操作・`doKeys`・ツールバー要求枠・持ち物のドラッグ等の全入口に共通の操作者判定を置く。主ウィンドウの閉じる操作は例外として、CLI所有中は拒否し、手動への切替を案内する。manual所有中は通常のsave／quitを入力待ちへ配送する。

agent対応起動の`closeEvent`や保存・終了メニューから`dosave0`・`done`・`nh_terminate`を直接呼ばない。`lastWindowClosed`による自動終了も止める。どの正常な終了も、共通の最終結果の出力・記録を通す。

agent対応起動の各入力関数は、コアへの呼び出しを抜けず、手動UIとCLIのどちらの有効な応答を使うか待つ共通ループにする。Qtのダイアログは表示手段であり、その`exec`の戻り値を無条件に取消へ変換しない。操作者切替には通常のreject／ESCと異なる専用の表示終了理由を使い、回答なしに表示を閉じたり再表示したりする。CLI所有中は同じ質問を読取り専用・非モーダルに表示する。古い表示世代のfinished等の信号は入力として採用しない。

切替は現在の入力待ちで行う。追加質問の途中でも質問そのものを保存し、回答や取消を補わずに操作者だけを変える。入力バッファと未適用の応答を整理し、版と質問IDを更新する。古いCLI応答は実行できない。すでに適用を始めた行動を取り消したことにはしない。

処理中の切替要求は保留の意図として記録し、その行動が次の入力待ちへ戻ったときに適用する。GUI側からの手動切替が保留されている間は、新しいCLIの行動予約を拒否する。処理中にコアを別スレッドから強制停止しない。画面なしで`manual`への切替を求めた場合は`unsupported_view`で拒否する。

manualからcliへの切替も、認証済みの利用者が明示した`controller.set`を許可する。再接続や`not_controller`を理由にクライアントが自動で操作権を奪い返す処理は作らない。GUIからの手動切替が保留中の新しいCLI行動は`not_controller`で拒否する。

## 6. 切断・EOFと中断

CLIのEOF、通信切断、CLIプロセスの終了は、ゲームのEOFや`hangup`へ渡さない。ゲームの実行先を残し、入力待ちならそのまま待ち、処理中なら受付済みの行動が次の入力待ちへ到達するまで進める。接続がないことを理由に追加のターン、ESC、待機、保存、終了を発生させない。

接続が戻るまでの自動終了期限は設けない。再接続で同じ受付記録を照会できる。画面ありなら手動へ切り替えて続けることもできる。OSによる実行先の終了・電源断・致命的な異常と、CLI接続だけの切断は区別し、前者の回復はコアの通常の回復範囲と最終結果の有無で判断する。

この待機規則は現在のターン駆動コアの入力待ちを対象とする。今後のリアルタイムのゲーム規則を、この仕様で停止型へ固定するものではない。リアルタイムの時間進行を追加するときは、通常操作とCLIで同じ時計の規則を別途定める。

`operation.interrupt`は通常の行動要求とは別の制御要求とする。通信層が中断の意図を記録し、コア側が次のターン境界で消費する。作業、回数付き待機・探索、走行・移動の継続を対象にし、`stop_occupation`・`reset_eat`・`nomul(0)`・`end_running`等の該当する通常の停止処理へ接続する。呼び出し元の状態と戻り処理はコアで判定する。追加の1ターンを消費させる中断コマンドは作らない。

飲食や装備・読書等の中断後の状態は、コアの既存の中断規則に従う。麻痺・気絶・必ず進める処理、セーブ書き込み中、1つの攻撃や品物処理の途中を強制的に切らない。即座に中断できるかどうかの判定に非公開状態を使った説明を返さず、受付と実際に入力待ちへ戻ったことを分けて通知する。中断不能な処理では次の安全な境界まで保留する。

Windowsにある`WIN32CON`・`nt_kbhit`の分岐の有無に機能を依存させない。共通のターン境界の接続を追加し、Unixでも同じ停止規則を通す。画面ありの手動の中断も同じ接続へまとめる。型付きの中断フラグを未処理のESCキーとして入力キューへ残さない。

## 7. ビルド・配布・受け入れ

既存のソース準備、Windowsのnmake、Unixのmakeへ、共通コア・agentウィンドウポート・CLIと必要なリンク先を加える。生成済みファイルだけを手直ししない。Qt Networkを追加するため、Windows配置処理の`Qt6Network.dll`削除一覧も見直し、各実行先の実際の依存関係に基づいて配置を検査する。

| 検査 | 合格条件 |
|---|---|
| 画面なしの起動 | GUI／Widgetsをリンクせず、LinuxではDISPLAY・WAYLAND_DISPLAY・QT_QPA_PLATFORMがない環境でも通常の冒険を継続できる |
| 画面ありの起動 | 通常のQt画面を表示し、CLIから開始・選択・移動・基本動作ができる |
| 共通コア | 同じ言語・設定・検証用セーブと操作列で、コア状態・本体乱数・表示用乱数を既定の境界で比較する |
| 接続と切断 | 再送・再接続・2本目接続の拒否・EOFで入力が混ざらず、自動ターンやESCが起きない |
| 保存先 | 初期化前から分離され、非ASCIIのルートでも動作する。通常のセーブ・設定と混ざらない |
| 操作者 | 版と質問の失効、処理中の保留、CLI／手動の相互抑止が機能する |
| 中断 | 対象ごとの安全な停止境界と中断不能な範囲を検査し、未対応を対応済みにしない |
| 終了 | 最終イベントとセッション別の最終結果を照合でき、古い結果を今回の結果と誤認しない |

C1〜C4の各段階で英日・画面あり／なしを確認する。Windows以外は、ソース・ビルド・実行のどこまで確認したかを分けて記録し、未実行を合格にしない。

## 8. 根拠と確認範囲

現行のランチャーはQApplicationを作り、通常起動では言語別Qt実行先を起動するため、そのまま画面なしのCLIとして流用しない。GUIの初期化と通常のQt操作は`src/launcher.cpp`、生成済み`qt_bind.cpp`、保存先の設定は`scripts/prepare-source.ps1`と`build-unix.sh`を調査した。

ローカルQt 6.11.2の`qlocalserver.h`で`UserAccessOption`・`setSocketOptions`・`listen`の宣言を確認し、OS別の許可の差は上記のQt公式仕様を確認した。非GUIのQCoreApplicationとWidgets用QApplicationの区別も[Qt公式資料](https://doc.qt.io/qt-6/qguiapplication.html)に従う。これは設計の根拠であり、本書の構成のビルド・動作が検証済みという意味ではない。
