# CLI操作とエージェントによるプレイの追加仕様

状態: 2026-10-27にC0設計を確定。2026-10-28にC1の実装へ着手した。[実装・検証記録](agent-play-cli-implementation.md)を参照。CLIで通常のゲームを操作できる段階には達していない。

共通の要求・応答は[C0の詳細設計](agent-play-cli-design.md)、両実行形態の起動・接続・制御は[実行構成](agent-play-cli-runtime.md)、コマンドと入力・表示の全経路は[接続仕様](agent-play-cli-inputs.md)に定義した。Claude Codeの区切りのレビューでC0設計完了と判定された。実装・動作確認とは区別する。

## 1. 目的と確定している要求

レモンの追加要求は「ゲーム操作をCLIからも行えるようにし、エージェントがゲームをプレイできるようにする」。起動や固定手順の試験だけでなく、エージェントが状況を読み、次の行動を選び、通常の冒険を継続できる操作口を設ける。

- C/C++の通常ゲームコアを利用する。CLI用に別のゲームルールを実装しない。
- 移動、Space相当の基本動作、戦闘、持ち物・装備・道具・魔法、扉、階段などの操作を対象にする。
- 行動の途中に発生する方向指定、品物選択、複数選択、数値・文字入力、確認にも応答できるようにする。
- 新規開始、キャラクター選択、保存、終了、再開、死亡・終了結果の確認まで扱う。
- 英語・日本語に対応する。機械向けの項目名と操作IDは言語に依存させない。
- 既存のQtによるプレイも維持する。描画品質の改善仕様、Antigravityへの画像制作依頼、各段階でのClaude Codeレビューは継続する。

本書はゲームルールの細部を固定しない。今後ルールを変更するときも、QtとCLIで同じコアの操作を実行する。

## 2. 確定した実行形態

2026-10-27、レモンが選択肢1「画面なし・画面ありの両方」を選択した。両方で同じ操作APIと通常のゲームコアを使う。

| 候補 | 利用例 | 構成への影響 |
|---|---|---|
| 画面なし | エージェントだけで遊ぶ | GUIを初期化しない専用の実行先とagentウィンドウポート |
| 画面あり | Qt画面でエージェントのプレイを見る／手動と切り替える | 操作APIを有効にした専用起動のQtゲームと入力の調停 |

具体的な起動・接続・切断・中断・操作者切替は実行構成に定める。文書にあるファイル名・CLI引数・APIは実装する仕様であり、現行アプリで利用可能という意味ではない。

## 3. エージェントが読む情報

通常のプレイヤーに提示できる情報を、機械で扱える観測として返す。観測を取得するだけではターン、位置、HP、乱数、鑑定・観察状態を変更しない。

| 情報 | 返す内容と制限 |
|---|---|
| セッション | 言語、API版、ビルド識別子、現在の入力待ち種別、観測の版番号、通常／デバッグ等のモード、試験用乱数固定の有無 |
| 主人公 | 画面に表示する位置・階情報、HP、魔力、能力、空腹・状態異常など。コアが表示しない詳細は除く |
| 地図 | 現在見えているもの、記憶しているもの、未探索を区別する。見えない現在の地形や敵の移動を記憶へ反映しない |
| キャラクター・品物 | コアが表示用に決めた姿と、表示用情報から副作用なく得られる説明。検知のみ・不可視・幻覚・未観察などの制限を維持する |
| 持ち物・装備 | 通常の一覧で知り得る説明、個数、装備状態、画面にも提示する持ち物の文字（invlet）。未鑑定の効果や未確認の状態を追加しない |
| メッセージ | 順序付きのメッセージと前回からの取得位置。省略や取りこぼしを検出できるようにする |
| 入力要求 | 質問文、選択肢、単一／複数選択、数量、既定値、取消の可否など、通常の画面で提示する内容 |
| 終了結果 | ゲームが通常提示する死亡・勝利・中断などの結果。終了後の入力可否 |

地図の座標はゲームのマス座標を使い、ウィンドウサイズやズームから独立させる。表示用の地形・対象の意味を返す方式とし、ASCII画面をエージェントに読み直させる方式だけに限定しない。見える／記憶の区別は、表示バッファとQtにも使う表示用のフラグを根拠にする。新しいメタデータが必要なら、コアが表示を通知する箇所で範囲を定義する。地形・敵・視界の内部配列をそのまま外へ返さない。

観測は`putstr`、`add_menu`、`print_glyph`、`status_update`、`update_inventory`などの経路で受け取った、版を揃えた表示用スナップショットから作る。観測要求や再送のたびに`xname`・`doname`・`obj_to_glyph`などを呼ばない。名前生成には観察状態の更新、幻覚の表示選択には乱数消費が伴うためである。名前や持ち物表示を作る時点をQtとCLIで共通にし、通常の持ち物を開く操作による正規のコア更新と、受信済み一覧を再取得する観測を区別する。描画とCLIで同じ情報保護の規則を適用する。

`print_glyph`だけでは対象の個別の名前を受け取れない。地図の通常の観測では、受信済みの表示分類とR2の外見グループから副作用なく得られる説明までに限定する。個体名や詳細が必要なときは、遠見などの正規のコアの調査操作を行い、その表示結果を返す。観測のために実体から個別の名前を生成しない。

[R2のアイテム外見仕様](item-appearance-contract.md)を観測・メニューの`add_menu`・イベント・ログにも適用する。本物と偽物など同じ外見の品を、真の種類、raw glyph、tileidx、画像ファイル番号などで区別できる出力にしない。

選択IDはその入力要求の選択肢だけに割り当て、応答・取消・更新で失効させる。別の質問や観測をまたいで同じ個体を追跡するIDにはしない。持ち物の指定には、通常の持ち物のinvlet、質問内の選択ID、コアがその質問で許す素手・なしを使う。強調されない候補も通常の入力経路で指定でき、適否はコアが判定する。地図上の対象は座標と現在の表示情報で指定し、敵・床の品物・擬態などに永続IDを付けない。表示改善で使うキャラクター・物体の内部IDもCLIへ出さない。選択肢の文面、順序、数量を超えて区別を追加しない。

デバッグ用の全地図・内部型・乱数・検証用セーブ生成は、通常のプレイAPIから分離する。通常の観測に混ぜず、エージェントが遊べることの合否を特権情報に依存させない。

## 4. 操作と入力待ちの設計案

エージェントが日本語・英語の文面を推測してキーを連打しなくてよいよう、構造化した操作と入力要求を用意する。

| 操作群 | 内容 |
|---|---|
| セッション開始・再開 | 実行構成のstart引数で起動時に言語と専用プロファイルを確定し、開始時の選択にも応答する |
| 観測 | 最新状態、未取得のメッセージ、現在の入力要求を取得する |
| 移動 | 方向を指定する。移動先の戦闘や扉の処理は通常のゲームコアに委ねる |
| 基本動作 | Spaceと同じ`contextaction`を呼ぶ。CLI側で対象判定を再実装しない |
| 通常コマンド | 持ち物、拾う、置く、武器、装備、道具、容器、扉、階段、食べる、投げる、射撃、探索、待機、魔法などを安定したIDで指定する |
| 質問への応答 | 入力要求IDを指定し、方向・確認・品物・複数選択・数量・文字列・位置・続行・取消を応答する |
| 保存・終了 | 通常のコア経路で実行し、必要な確認に応答する。保存成功とプロセス終了を別々に報告する |

通常コマンドの一覧と、その時点で入力できる形式を取得できるようにする。ただし「試せるコマンド」を「必ず成功する行動」とは扱わない。隠し扉や罠の有無、敵の実際の能力などを使って成功可否を先に教えない。

操作IDは元の英語の拡張コマンドの完全名を基準にし、言語別のコア定義へ明示的に対応付ける。コマンド番号、翻訳文、利用者のキー割当を外部IDにしない。拡張コマンドに収まらない移動・応答・開始終了の操作には別の固定IDを定義する。日本語側の名前や確認用キーの違いもC0で照合する。

状態は、起動中、通常コマンド待ち、追加応答待ち、処理中、終了に分ける。開始前の選択も追加応答待ちに含める。接続の状態は別に持ち、切断中もコアがどの入力要求で停止しているかを保つ。追加応答待ちには要求の種別とIDを付け、コマンド入力と応答を混同しない。取消できない質問も表現する。状態に合わない要求と古い入力要求への応答は、入力をコアへ渡す前に拒否する。

入力待ちは、翻訳済みの質問文や候補文字列を解析して判別しない。`yn_function`だけでは方向・品物・確認を区別できないため、コアの呼び出し元で種類と提示可能な選択肢を付ける接続を設計する。`program_state.input_state`だけにも依存しない。C0では次の全経路を照合し、識別と応答の対応表を作る。

| 入力待ち | 主な発生元・接続先 | 構造化する内容 |
|---|---|---|
| 通常コマンド | コマンドループ、`nhgetch`／`nh_poskey` | コマンドID、移動方向、必要なら表示上の位置 |
| 方向 | `getdir` | 許可する方向、自己・上下、取消 |
| 品物 | `getobj`、持ち物・床・容器の選択 | 通常の持ち物のinvletまたは質問内の選択ID、許可された素手・なし、一覧への遷移、数量。強調された候補だけに限定しない |
| 単一・複数メニュー | `select_menu`、`message_menu` | 選択肢、選択数、数量、取消、ページがある場合の全候補への到達方法 |
| 確認・数値 | `yn_function`、`get_count`などの呼び出し元 | 選択肢、既定値、上限下限、取消の可否 |
| 文字列 | `getlin`、名前入力 | 目的、UTF-8のバイト上限、空文字・取消の区別 |
| 位置 | `getpos`と`readchar_poskey`の入力ループ | 座標、決定、取消、通常許される対象の制約。任意座標の応答経路を設計し、隣接方向のキューで代用しない |
| 続行・ページ送り | メッセージの`display_nhwindow(..., TRUE)`、物語・ヘルプ等 | 続行、ページ送り、閉じる、取消の可否 |
| 開始前・終了時 | 言語・セーブ・キャラクター選択、死亡後の質問・公開・結果 | Qt固有の画面もCLIで同じ内容を扱い、結果の出力前にプロセスを終了しない |
| 未分類のキー入力 | 上記に分類できない`nhgetch`等 | 明示的な未対応イベント。入力を捏造せず停止を診断し、必須経路は実装時に解消 |

1回の操作で1ターン進むとは限らない。持ち物表示は時間を進めない場合があり、移動は戦闘へ変わる場合があり、休息・作業・走行は複数ターン継続する。応答には、受け付けたか、入力待ちに戻ったかを分けて記録する。ターンが進んだかの公開もコアの通常表示の範囲を守り、数値等が非公開ならnullとする。内部の正確なターン比較は試験側で行う。処理中の新しい行動要求は`busy`として拒否し、次の質問へ勝手に流れる入力キューにしない。

Windowsの現行ビルド設定では、作業中の`kbhit`／`pgetchar`による中断分岐が有効になり、Qtの初期化で`nt_kbhit`をQtのキー検査へ接続している。初回レビューの「Qtビルドには経路がない」という説明は、この接続まで確認した結果と異なるため訂正する。実行構成では、安全なターン境界で通常の停止処理へ渡す共通接続を追加する。各対象・OSで実装と検証が済むまでは、中断を利用可能な能力と表示しない。将来リアルタイムのルールを追加する場合の待機中・切断中の時間進行も、コアと両操作方法で共通の仕様として別途定める。

中断要求は通常の新しい行動要求と区別し、処理中にも専用の制御意図として受け付ける。コアの安全な境界で適用し、受付と停止完了を区別する。対象と中断不能な範囲は実行構成に従う。

コアが次の入力を要求した時点を操作結果の区切りにする。追加質問が発生した場合は、その質問を含む観測を返し、エージェントの応答を待つ。表示アニメーションの完了をゲームの入力待ちと取り違えない。

## 5. CLIと通信の設計案

機械向けにはUTF-8のJSON Linesを使う。コンソール用CLIの標準出力は機械向けのデータだけとし、診断は標準エラーへ出す。ゲームとはローカルIPCで接続し、現行のWindows GUI実行ファイルの標準入力へキーを流す方式にしない。人向け表示は明示的に選ぶ。具体的な実行先、引数、通信路、接続の識別、終了コードは実行構成に定義する。

要求・応答にはAPI版、セッションID、要求ID、観測の版番号を含める。要求IDと入力要求IDは別の役割とする。

- 行動要求は観測の版番号を指定する。状態が変わっていれば、古い判断で実行せず最新の観測を返す。
- 一度にコアへ適用する行動・応答要求は1つとする。通信層から直接コアを呼ばず、通常の入力処理と同じ実行コンテキストで直列に適用する。通信層はコアの状態を直接読むことなく、確定済みの要求処理状況から`busy`・状況確認・再送への応答を返せるようにする。処理中の観測を許す場合は最後に公開したスナップショットと処理中であることを返し、途中のコア状態を読み取らない。
- 同じセッションで同じ要求IDを再送した場合、コアへ作用する要求は、内容が同じなら保持している結果または処理中の状況を返し、再適用しない。内容が異なる場合は拒否する。読み取り専用の要求は内容一致を確認してから公開済み情報で再評価できる。いずれもコア状態へ副作用を起こさない。この重複判定は観測の版番号の照合より先に行い、実行済み要求の再送を古い版として誤判定しない。結果の保持範囲と再接続時の確認手順はC0の詳細設計に従う。
- 待ち時間の超過は、操作失敗・未実行の証明にしない。要求IDで処理状況を確認し、タイムアウトを理由に新しいIDで同じ行動を自動再実行しない。
- 入力不足、状態不一致、未対応コマンド、保存失敗、プロセス終了を区別し、機械向けのエラーIDと説明を返す。
- 不正なJSON、数量・座標の範囲外、未提示の選択IDを拒否する。文字列の上限はコアの`BUFSZ`・`PL_NSIZ`等に合わせたUTF-8のバイト数で定義し、文字の途中で切り詰めない。英語版でもUTF-8を共通に扱う接続を実装し、現行のLatin-1変換をそのまま通して文字化けさせない。通信レコード全体のサイズ上限と回復規則も詳細設計で決める。

メッセージはコアの表示抑止設定を尊重し、セーブから戻した履歴を新規の出来事と区別する。未接続中の保持件数と超過時の欠落通知、取得カーソルの有効期間をC0で決め、取得に成功したふりで履歴を落とさない。

画面ありでは操作者をCLI／手動から明示的に選び、双方のゲーム入力を同時に受けない。追加質問の途中の切替も、質問へ答えたり取り消したりせずに行う。切替で版と質問IDを更新し、古い応答を失効させる。処理中の切替は次の入力待ちまで保留する。

ローカルIPCでの利用を対象とし、TCPを待ち受けない。実行構成のセッションID・利用者限定の接続情報・相互認証で、別セッションや別の接続先を取り違えないようにする。

## 6. 保存・設定と通常プレイ

言語別の保存互換性と分離は既存方針を引き継ぐ。エージェント用には明示した専用プロファイルを使い、セーブ、NetHack設定、ロック、ログ、骨ファイルなどコアが書くデータ、Qtを使う場合のQt設定まで分離する。通常のセーブ・設定を上書きしない。保存のロック、二重起動、保存失敗はコアの経路で扱う。現行の通常起動の保存先初期化にも接続の変更が必要であり、既存環境変数だけで実現済みとは扱わない。

保存して再開したときの、セッションID、選択ID、観測の版番号の有効期間を定義する。新しいプロセスで古い入力要求へ応答できないようにする。ゲーム用セーブと通信履歴の役割を分け、要求の重複適用を避ける。

通信切断やEOFを待機キーやESCの自動補完に変換しない。現行コアのEOFによる`hangup`／`end_of_input`や、Qtの例外時のESC補完を、CLI接続の障害処理に使わない。実行先を残し、受付済みの行動が次の入力待ちへ進んだ後は再接続を待つ。自動の追加ターン・保存・終了は行わない。実行先自体の異常終了・電源断・コアの保存不能と、接続だけの切断は区別する。必ず保存できるとは約束しない。

現行の`DARKDUNGEON_SMOKE_OUTPUT`は検証用であり、通常プレイのCLIに流用しない。`scripts/prepare-source.ps1`では検証時の乱数固定や自動入力を組み込み、`src/qt_darkdungeon.cpp`では検査と終了を行っている。CLIの通常利用で、この環境変数や検証用の内部状態変更を必要としない構成にする。

試験用の乱数固定は、専用プロファイルの指定と独立した試験専用設定とし、通常プレイの既定では無効にする。通常プレイAPIからの内部乱数取得と、試験ハーネスが起動時に種を指定することは分ける。

開始前の言語・セーブ選択・キャラクター選択・物語と、死亡後の確認・所持品公開・墓石等は、現行でQt固有の画面を含む。CLIでは同じコアを使うゲーム行動と区別して、同じ選択内容と終了結果を提供する。正常終了では`exit_nhwindows`／プロセス終了より前に最終応答を出力・フラッシュする。保存の成功がそのままプロセス終了を伴う経路も扱い、保存後に同じプロセスが継続するとは前提にしない。再開時のセーブ消費・ロック処理はコアの実装を照合し、元の検証用セーブを直接消費せずコピーで確認する。

| 段階 | 作業 | その段階で実行する確認 |
|---|---|---|
| C0 仕様・接続設計 | 実行形態、観測、全入力待ちの識別と応答、通信、保存、切断、中断、必要な入力調停を確定 | 要求と入力経路を照合し、未確定事項を解消してClaude Codeで設計レビュー |
| C1 開始・観測・基本操作 | 共通コア、両viewの実行先、専用プロファイル、接続、新規開始、地図・状態・メッセージ、移動、基本動作、必要な方向・品物・確認・More等への応答、基本の保存・終了・再開、未分類入力の検出 | 英日・画面なし／ありで開始し、観測→判断→移動を繰り返せる。質問から復帰し、専用データで保存・終了・再開できる。観測だけでは状態が変わらない |
| C2 通常操作・追加応答 | 通常コマンドの対応表、方向・品物・数量・文字列・位置・確認・取消 | 拾得、装備、容器、戦闘、扉、階段、魔法を操作し、入力待ちから復帰できる |

C1以降は各段階で操作可能な確認版、起動手順、機械向けログを残す。各段階の区切りでClaude Codeへ読み取り専用レビューを依頼し、重大な未解決事項があれば完了にしない。ビルド・言語・専用プロファイル・実行手順・結果を記録する。

C1〜C4の全段階を英語・日本語の両方で検証する。一方の言語の成功だけで段階完了としない。

C1を、共通コアと画面なしポート、初期化前の保存先分離とIPC、英日UTF-8と共通スナップショット、Qtとの接続、端末CLI、両viewの確認版検証へ分ける。基本の保存・終了をC1から提供し、C3で再送・失効・切断・保存失敗・操作者切替等の障害時まで検証を広げる。

ソース準備処理とUnix用パッチも対応範囲へ含める。Windows・Linux・macOSの実行検証を分けて記録し、未実行OSを動作確認済みと報告しない。検証担当や実行できない環境は実装計画時に明記する。

CLIは、表示改善の操作試験にも利用できる。ただし画面なしの試験だけでは、画像、重なり、配置、アニメーション、カメラの合否を判定しない。表示改善の各フェーズで定めた画面・動画・Qt上の確認は引き続き必要とする。

## 8. 受け入れ条件

| ID | 条件 |
|---|---|
| CLI-01 | 外部エージェントが公開したCLI仕様だけを使い、固定済みの試験操作に依存せず通常の冒険を継続できる |
| CLI-02 | 移動と基本動作がQtと同じコア経路を使い、対応する初期状態と操作列でゲーム結果が一致する |
| CLI-03 | 新規開始から終了までの全入力待ちを分類し、未対応の入力待ちによる停止を検出できる。通常プレイの必須経路に未対応がない |
| CLI-04 | コアが通常表示する視界・記憶・検知・幻覚・未鑑定情報の制限を守る。隠れた情報だけを変えた比較でも観測が漏えいしない |
| CLI-05 | 観測を繰り返しても、位置・HP・ターン・鑑定／観察／発見フラグを含むセーブ相当の状態と乱数が変わらない。ログ取得、通信再送、再描画にも同じ条件を適用し、同じ要求の再送で行動を重複適用しない |
| CLI-06 | 英日で操作IDと入力形式が共通し、表示文・入力文・プレイヤー名をUTF-8で扱える |
| CLI-07 | 専用プロファイルで保存・終了・再開でき、通常のセーブ・設定を変更しない。保存失敗を成功として返さない |
| CLI-08 | 死亡、終了、継続操作、中断、タイムアウト、切断、古い応答を区別し、再接続・復帰できる範囲と限界を検証する |
| CLI-09 | 採用した実行形態それぞれで動作を確認する。画面ありを採用した場合はCLIと手動入力の競合も検証する |

CLI-02の比較では、同じビルド・言語の専用環境を2つ用意し、試験専用の同じ乱数設定、同じ開始条件または同じ検証用セーブのコピーから始める。Qt側にも対応する操作列を入力し、入力待ちの区切りごとにステータス・表示用地図・メッセージ・セーブ相当のコア状態・乱数を比較する。UI設定や実行時刻等の差は比較対象と除外理由を記録する。特権の比較データは試験側で取得し、通常のエージェントへ渡さない。特権の比較試験と、CLI-01の通常プレイの試験は別々に実行する。

乱数はゲーム本体の乱数と、幻覚等の表示用乱数（`rn2_on_display_rng`）を区別する。CLI-05では観測・再送・再描画によって双方が進まないことを検証する。CLI-02では本体の乱数の一致を必須とし、表示用乱数も共通の表示生成の境界に揃えて比較する。C0でその生成時点と回数を定義し、画面の再描画回数や観測回数で表示用乱数を追加消費しない構成にする。表示用だからという理由だけで不一致を合格にしない。

CLI-04では、同じ外見の敵の入れ替わり、視界外での品物の移動、擬態、本物・偽物、幻覚、観測の再取得、メニュー更新も検査し、ID・順序・ログから余分な追跡情報が漏れないことを確認する。
